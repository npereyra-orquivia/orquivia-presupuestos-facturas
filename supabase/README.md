# Orquívia: empresa compartida en Supabase

La interfaz se publica en GitHub Pages; los datos reales y los justificantes privados permanecen en Supabase. Nicole administra la empresa y el saldo inicial; Liliana edita clientes, presupuestos, facturas, cobros y gastos en el mismo espacio. Los correos y contraseñas para crear sus cuentas se pasan al script de servidor mediante stdin, nunca al código público.

## Activar el proyecto

1. Aplica **las catorce migraciones en orden**: `202610130001_orquivia.sql`, `202610140002_team_production.sql`, `202610140003_expenses.sql`, `202610140004_personal_profiles.sql`, `202610140005_push_runtime.sql`, `202610140006_personal_identity.sql`, `202610140007_expense_quick_entry.sql`, `202610140008_vat_document_status.sql`, `202610140009_record_history.sql`, `202610140010_tax_records_missing_receipts.sql`, `202610150011_prepared_quotes.sql`, `202610150012_document_mail.sql`, `202610150013_mail_recipients.sql` y `202610230014_invoice_mail.sql`. Con CLI enlazada al proyecto, `supabase db push` aplica las pendientes. La tercera crea gastos y el bucket privado `orquivia-receipts`; la cuarta añade perfiles personales, dispositivos y `orquivia-avatars`; ambas necesitan el esquema administrado `storage` de Supabase. La quinta crea la configuración privada del servicio push, sin incluir claves en el código. La sexta exige que la identidad final del JWT coincida con la usuaria capturada antes de transportar cada petición personal. La séptima permite proveedor opcional, IVA desconocido, importes adicionales, abonos y movimientos de caja separados. La octava admite anotaciones explícitas de evidencia fiscal sin confirmar el desglose del IVA. La novena añade auditoría detallada por registro sin alterar los datos históricos. La décima añade declaraciones fiscales y motivos de falta de ticket. La undécima permite preparar un presupuesto numerado antes de marcarlo como enviado, sin modificar estados ni números existentes. La duodécima incorpora las credenciales de correo cifradas en Vault y los envíos privados; la decimotercera permite varios destinatarios y copias; la decimocuarta permite enviar facturas emitidas y registrar su entrega sin alterar los cobros. Consulta [EMAIL-V1.1.md](../EMAIL-V1.1.md) para desplegar la función de correo. En un entorno existente aplica solo las pendientes. Mantén `orquivia_private` fuera de los esquemas expuestos de Data API; expón `public`.
2. Desactiva el registro público en Supabase Auth. Ninguna cuenta obtiene membresía automáticamente, aunque alguien consiga crear una cuenta en Auth.
3. Ejecuta `scripts/bootstrap-team.mjs` desde un entorno de operador con la clave privada del proyecto y los dos usuarios autorizados. Recibe un único objeto JSON por stdin con `url`, `serviceKey`, `admin: {email,password,name}`, `editor: {email,password,name}`, y opcionalmente `organizationId`, `statePath`, `requireMfa`, `overwrite`, `expectedVersion`, `expectedHash`. Las contraseñas iniciales deben tener al menos 16 caracteres.
4. Por defecto el script solo valida localmente y no hace llamadas de red. `apply:true` crea las cuentas que falten sin enviar invitaciones, confirma sus direcciones según la provisión autorizada, asigna Nicole como `admin` y Liliana como `editor`, exige MFA y opcionalmente importa el archivo privado indicado. Las cuentas que ya existan conservan sus contraseñas. No muestra ni guarda credenciales. Entrega las contraseñas por el canal privado elegido por sus titulares.
5. Configura únicamente URL y clave **publishable** (o **anon** antigua) en la interfaz/variables Vite. Ninguna clave `service_role`, `sb_secret_…` ni contraseña pertenece al navegador, GitHub o una variable `VITE_…`.

El script no revierte cuentas ya creadas si falla un paso posterior; comprueba el resultado antes de repetirlo. La pertenencia existente evita mover cuentas silenciosamente entre empresas. Un rerun correcto reutiliza la empresa de Nicole; una organización diferente debe indicarse explícitamente. La importación solo procede sobre un espacio recién creado en versión 1. Un resultado ya importado se reconoce mediante SHA-256 estable y se omite sin subir la versión. Si existen cambios posteriores, el script se detiene. Una sustitución deliberada requiere `overwrite:true`, la versión actual y el SHA-256 del estado actual en `expectedVersion` y `expectedHash`; el CAS de la base de datos sigue protegiendo cambios simultáneos.

Estos archivos describen el procedimiento de provisión y actualización. Antes de ejecutar una migración o importación sobre un proyecto existente, comprueba su historial de migraciones y conserva una copia del estado y de los justificantes.

## Acceso y sesiones

`orquivia_memberships` autoriza cada usuario mediante su UUID de Auth y un rol explícito. `anon` y usuarios autenticados ajenos a la empresa no pueden ver datos. Los miembros solo tienen lectura directa de tablas; escriben a través de RPC que vuelven a verificar la membresía. Solo un operador con clave de servidor puede provisionar usuarios, membresías o importar históricos. Liliana puede trabajar con documentos, cobros, gastos y sus adjuntos; los datos de empresa, saldo inicial, IBAN y correo para avisos los modifica Nicole.

El cliente guarda tokens en `sessionStorage`, no en almacenamiento persistente del navegador. `refreshAccess()` llama a la RPC `refresh_orquivia_access`, que vuelve a comprobar membresía y requisito MFA en el servidor sin devolver datos del espacio. La interfaz debe bloquearse ante `ACCESS_REVOKED`, `MFA_REQUIRED` y `SIGNED_OUT`; los dos primeros eventos vacían la empresa y la versión del cliente, por lo que tras recuperar acceso hay que cargar de nuevo. Cada lectura/escritura RPC también comprueba acceso. La revocación no puede borrar una copia que un usuario autorizado ya haya descargado.

Durante una recarga, la pantalla **Comprobando tu sesión…** permanece visible hasta resolver la sesión, la membresía y MFA; el formulario de acceso aparece si es necesario identificarse. La navegación usa rutas permitidas en el fragmento de la URL y un estado por cuenta en el `sessionStorage` de cada pestaña. Se restauran la sección, filtros de presupuestos/facturas/gastos, búsquedas y selección del período de informes después de autorizar la carga. Los términos de búsqueda no se incluyen en la URL. Atrás y Adelante recuperan las rutas. El instante de actividad se conserva por cuenta para que recargar no eluda el bloqueo por 30 minutos de inactividad. Esta persistencia no guarda formularios pendientes ni permite mostrar datos antes de verificar el acceso.

El backend ofrece TOTP con `mfa.enroll`, `mfa.challenge`, `mfa.verify`, `mfa.factors` y `mfa.assuranceLevel`, además de cambio de contraseña comprobando primero la actual y cerrando otras sesiones de renovación. Supabase puede mantener un JWT ya emitido hasta su vencimiento; no se promete invalidación instantánea de todas las copias.

El script de provisión de producción configura explícitamente `require_mfa=true`; la interfaz permite inscribir el autenticador en el primer inicio de sesión antes de cargar datos. Las RPC y las políticas de lectura exigen `aal2`. El valor SQL por defecto sigue siendo `false` para migración y pruebas antiguas; un entorno de desarrollo puede pasar `requireMfa:false` expresamente. Prueba alta, verificación y recuperación con las dos titulares antes de dar por terminado el despliegue.

## Contrato de la aplicación

- `loadState()` resuelve la empresa por membresía y devuelve el estado compartido. Una cuenta ajena recibe `MEMBERSHIP_REQUIRED`; no se crea un espacio de demostración como sustituto de datos reales.
- `workspaceInfo()` devuelve `{organizationId,name,role,requireMfa}` después de cargar.
- `saveState(state)` compara la versión actual y guarda con CAS. Cada dispositivo debe cargar primero; un conflicto obliga a conciliar cambios y recargar. Los nuevos documentos se guardan como `draft`, con `number:''`.
- `issueDocument(documentId)` emite el borrador ya guardado y devuelve `{state,version,updatedAt,documentNumber}`. La interfaz sustituye su estado con ese resultado. El servidor asigna `F-AAAA-NNN` a facturas y `PR-AAAA-NNN` a presupuestos, en series separadas por empresa/tipo/año de emisión elegido.
- `auditLog()` permite consultar quién cambió el espacio, cuándo y en qué versión. Los miembros no pueden editar ni borrar el registro.
- `recordHistory(tipo,id)` consulta los cambios del registro y, para un documento, sus cobros asociados. La migración 009 inserta los campos modificados y la identidad de la sesión en la misma transacción del guardado o emisión. No conserva valores privados de perfiles ni credenciales; las claves desconocidas se resumen como `other`. Los miembros autorizados pueden leer el historial con MFA, pero no escribirlo ni borrarlo. El historial detallado empieza al aplicar la migración; la auditoría general anterior permanece intacta.
- `peekState()` permite comparar una versión remota sin actualizar la versión CAS local. Un conflicto sigue bloqueando guardados hasta una carga explícita; consultar el estado o el historial no habilita la sobrescritura de un borrador antiguo.

Los contadores y el registro permanente de numeración no son escribibles desde el navegador. Los números emitidos nunca se reutilizan ni se aceptan libremente del cliente. No se puede borrar un documento emitido ni revertirlo a borrador. Su número, tipo y fecha se conservan. Los datos de facturas emitidas quedan fijos, incluyendo título, forma de pago, metadatos originales y advertencias de importación. Solo notas, PO, contrato, vencimiento, revisión de cobro y metadatos de entrega siguen siendo editables, además del estado derivado de cobros y el total calculado. Los conceptos de presupuestos emitidos pueden actualizarse conservando su identidad. Los cambios quedan auditados. Un proceso de facturas rectificativas requiere una ampliación específica.

La migración `202610230014_invoice_mail.sql` añade `billingEmail` opcional a clientes y facturas como una única dirección de correo válida, sin espacios ni controles. La dirección operativa de una factura puede cambiar tras la emisión sin modificar su instantánea fiscal. Una factura emitida nueva empieza con `deliveryStatus:'ready'`; el envío aceptado por SMTP lo cambia a `sent`, incluso si falta guardar la copia en Enviados. Los envíos ambiguos, parcialmente aceptados o fallidos conservan el estado anterior. Este campo es independiente de `status` y de los cobros; la migración no clasifica ni reescribe facturas históricas. El servidor exige que la factura corresponda a su registro de emisión, conserva la idempotencia de cada solicitud y permite nuevos envíos deliberados con otra clave. Al completar un envío bloquea el espacio y fusiona solo el estado de entrega sobre la versión actual, preservando pagos y cambios simultáneos. El historial identifica la usuaria y los campos de entrega modificados. Las RPC de correo siguen reservadas a `service_role`, y la función Edge comprueba la sesión, la identidad, la membresía y MFA antes de usarlas.

La base de datos valida estructura y tipos JSON, precisión de importes/cantidades, calendarios reales, estados por tipo, sumas en céntimos, referencias a clientes/presupuestos/facturas, un único vínculo de factura por presupuesto y cobros positivos que no superen el total. No acepta un total almacenado distinto al calculado. El límite por empresa es 5 MB y 10000 registros por colección.

En el editor, la referencia interna del trabajo es opcional y no aparece en el PDF. PO es una referencia opcional de factura, que puede añadirse al convertir el presupuesto. La fecha prevista y la casilla de aceptación/contrato recibido son seguimiento opcional: modifican los avisos, sin aceptar automáticamente el presupuesto ni cambiar sus importes. Una factura convertida sigue como borrador editable hasta su emisión.

## Gastos y Storage privado

La migración `202610140003_expenses.sql` admite una colección `expenses` en el estado compartido, manteniendo compatibles los estados anteriores sin gastos. Valida descripción, fechas, importes con precisión de céntimos, desglose consistente, límites del IVA confirmado, estado del pago y fecha cuando está pagado. `202610140007_expense_quick_entry.sql` permite un proveedor opcional, abonos con importes negativos e `additionalAmount` separado del IVA, conservando la igualdad `base + vatAmount + additionalAmount = total`. También valida `cashAmount` y sus `cashMovements` cuando el pago bancario difiere del total documental o hay un anticipo y un reembolso en fechas distintas. Los importes reales del justificante son explícitos; un desglose sugerido por porcentaje no sustituye la revisión del documento.

Si `vatReviewNeeded:true`, no se admite `vatRate`, y `vatAmount` y `vatDeductibleAmount` deben ser cero en la representación interna. La base almacenada funciona como importe provisional para conservar el total; la aplicación devuelve `null` para base, cuota e IVA confirmado en los informes fiscales. No es una declaración de IVA cero.

`202610140008_vat_document_status.sql` permite el campo opcional `vatDocumentStatus`, exclusivamente con los valores de texto `included-unitemized` (**IVA incluido, sin desglose**) o `not-stated` (**Justificante sin datos de IVA**). Ambas anotaciones exigen `vatReviewNeeded:true` y conservan todas las validaciones de la migración anterior. El nuevo validador delega en `valid_state_expenses_quick_v2`, vuelve a vincular el CHECK del espacio y mantiene revocados los validadores privados para `public`, `anon` y `authenticated`; no modifica datos históricos.

La revisión operativa del justificante es independiente del estado fiscal y del pago: con un adjunto válido, una de esas anotaciones y `reviewNeeded:false`, el gasto puede salir del filtro **Por revisar**. La cuota desconocida conserva su etiqueta para el gestor y queda vacía en el CSV, igual que la base y el IVA confirmado. No se suma a los totales de IVA conocido ni se aprueba su deducibilidad. **Sin IVA** es una clasificación diferente que exige confirmar que no hay IVA en la operación.

Cada gasto admite hasta **10 adjuntos**, de **10 MB** (10 485 760 bytes) cada uno. El bucket `orquivia-receipts` tiene `public=false`, limita tamaño y tipos MIME, y admite PDF, JPEG/PNG/WebP/GIF/HEIC/HEIF, Word, Excel, OpenDocument y RTF. El cliente valida nombre, extensión, MIME y firma inicial del formato antes de subir. La opción de foto usa el selector/cámara que ofrezca el navegador; los bytes originales se conservan.

Los objetos usan rutas `organizationId/expenseId/attachmentId.ext`, con UUID y una extensión admitida. Las políticas de Storage verifican la membresía de esa empresa y el segundo factor cuando es obligatorio. No hay lectura anónima, sobrescritura ni traslado de originales desde la aplicación. Las políticas restrictivas mantienen esa frontera aunque posteriormente se añadan políticas generales para otros buckets.

El procedimiento de guardado es:

1. `uploadReceipt(expenseId,file)` sube cada original con un nombre nuevo y `upsert:false`.
2. `saveState(state)` guarda los metadatos `{id,name,path,mimeType,size}` junto al gasto mediante CAS. El servidor exige que cada objeto exista, pertenezca a la empresa y coincida en tamaño y MIME.
3. Para retirar un adjunto, guarda primero el gasto sin su referencia y después llama a `deleteReceipt(attachment)`. La base de datos impide eliminar un objeto que siga referenciado y serializa la eliminación con los guardados del espacio. La interfaz intenta limpiar las nuevas subidas si el guardado falla.

`downloadReceipt(attachment)` descarga con acceso autenticado y sin caché. `receiptUrl(attachment)` puede generar una URL firmada de 60 segundos, que también da acceso a quien la reciba durante su vigencia; la exportación del trimestre usa la descarga autenticada. Los archivos y sus referencias nunca se copian a GitHub Pages. El historial registra cambios y número de gastos; no guarda el contenido binario en la auditoría.

## Trimestre, copias y saldo

`quarterlyReport(state,year,quarter)` reúne facturas emitidas y gastos por la fecha del documento. Sus movimientos de cobro y pago se contabilizan por su propia fecha, incluso cuando el documento corresponde a otro trimestre. Se separan IVA repercutido, IVA soportado registrado e IVA confirmado para revisión. Los registros con IVA desconocido, incluidas las anotaciones de la migración 008, conservan el total y la evidencia, dejan su base/cuota/IVA confirmado vacíos en CSV y siguen identificados para el gestor aunque ya no requieran revisión operativa. La selección de IVA confirmado no determina por sí sola la deducibilidad ni presenta una declaración.

`quarterCSV` genera el listado y `buildQuarterBundle` prepara un ZIP con `registro-trimestre.csv`, `resumen.txt`, las facturas PDF y los justificantes originales. La exportación usa una instantánea validada y se detiene si falta un archivo o no coincide su tamaño, para evitar un expediente parcial. El límite es 300 MB. La **copia JSON incluye metadatos y rutas de adjuntos, no los archivos**; guarda también los expedientes ZIP. Restaurar los metadatos en otra base no transfiere automáticamente los objetos de Storage.

El saldo inicial se guarda en `company.openingBalance` y `company.openingBalanceDate` y solo puede modificarlo la administradora. Representa el saldo **al comienzo del día elegido**, antes de cualquier movimiento. Permite comenzar a registrar desde esa fecha sin importar todos los movimientos anteriores. Un ejemplo ficticio: saldo inicial de **2.500 €**, cobro posterior de **600 €** y gasto pagado de **100 €** dan **3.000 €** de saldo registrado. El saldo inicial no crea una factura, venta, gasto ni cuota de IVA.

`cashSummary` suma los cobros registrados y resta los gastos pagados desde esa fecha, incluida, hasta el día actual. Los movimientos anteriores están absorbidos en el saldo inicial y no vuelven a contarse. El histórico documental para informes es independiente: puede conservar documentos anteriores al punto de partida de caja; si se cobran o pagan después, el movimiento sí se contabiliza en su fecha real. Para reconstruir desde el comienzo, establece un saldo real y una fecha anteriores al primer movimiento. La previsión añade pendientes de cobro confirmados y resta gastos pendientes. Las facturas con cobro por confirmar se excluyen de los cobros previstos. La conciliación bancaria es manual.

## Importar los documentos originales

Los archivos privados y el JSON histórico validado deben permanecer fuera de `public/`, `dist/` y del repositorio publicado. El script de servidor lee `statePath` y llama a `import_orquivia_state`, que solo acepta la clave privilegiada y compara la versión para no sobrescribir cambios simultáneos.

Conserva números originales como `2026-002`; el servidor eleva el contador correspondiente sin renumerarlos. Los originales `2026-002` y `F-2026-002` representan la misma secuencia de factura y no pueden coexistir dentro de esa serie. Las series de presupuestos y facturas son independientes.

Cuando el PDF no demuestra si se pagó una factura, usa `paymentReviewNeeded:true` y `status:'issued'`. El portal y los correos piden revisar el cobro sin presumir que está impagado. Al confirmar un cobro, se registra el pago y se retira esa marca. Si una fecha original es incoherente, conserva la evidencia en `sourceMetadata`, deja `dueDate:null` y añade `importWarnings`; no inventes una fecha. Guarda discrepancias del total original en los metadatos y usa el cálculo consistente para operar.

Los espacios antiguos por usuario quedan conservados pero inaccesibles a la interfaz nueva. Un operador puede exportarlos y validarlos para una importación explícita; no se crean membresías a partir de ellos.

## Avisos con el portal cerrado

### Recordatorios personales y web app

`202610140004_personal_profiles.sql` conserva perfiles y dispositivos en tablas separadas del estado financiero. Cada usuaria solo puede leer y guardar su propio nombre, foto y preferencias mientras su membresía siga activa y su sesión sea `aal2`, incluso en una organización de pruebas sin MFA obligatoria. No hay escritura directa desde el navegador. El bucket `orquivia-avatars` es privado, admite JPEG/PNG/WebP de hasta 2 MB y usa rutas `organizationId/userId/avatarId.ext`. Un archivo vinculado al perfil no se puede eliminar y ninguno se puede sobrescribir. La interfaz recorta y reduce la foto antes de subirla; para retirar la anterior guarda primero el perfil sin esa referencia. La copia JSON de la empresa no incluye estos perfiles ni sus fotos.

Las preferencias personales `{enabled,payment,contract,review,daysBefore,onDueDate,repeatDays,hour}` están desactivadas por defecto. Los días se limitan a 0–30 y la hora a 0–23, en `Europe/Madrid`; un 0 desactiva la antelación o la repetición. `backend.personal` ofrece carga y guardado del perfil, foto, configuración pública del servicio y alta/baja de dispositivos. Las suscripciones pertenecen a la usuaria y su organización; se exigen MFA y proveedores push admitidos, con un límite de diez dispositivos activos. La revocación de membresía impide volver a leer el perfil o registrar dispositivos, y los objetivos del servidor excluyen usuarias revocadas o sin un factor verificado.

`202610140006_personal_identity.sql` añade el argumento obligatorio `p_expected_user_id` a la carga y guardado del perfil y a las operaciones de dispositivos. Las firmas anteriores quedan revocadas para las cuentas de la interfaz. El servidor compara ese UUID con `auth.uid()` antes de leer o escribir; si la sesión cambió mientras el SDK preparaba la solicitud, devuelve `AUTH_CHANGED` sin modificar el perfil o dispositivo de la nueva usuaria.

Para activar el servicio push:

1. Aplica las migraciones 004, 005 y 006 después de las anteriores. Despliega `supabase/functions/send-push-reminders` con verificación JWT del gateway desactivada: la función permite consultar la clave **pública** por GET, pero autentica cada envío POST mediante un secreto de cron privado. Con CLI: `supabase functions deploy send-push-reminders --no-verify-jwt --use-api`.
2. Haz una petición GET a la URL Edge `send-push-reminders`. El servidor genera una pareja VAPID una sola vez y la conserva mediante una escritura serializada. La clave privada y el secreto de cron permanecen en `orquivia_private.push_runtime_config`; no hay claves de servidor ni VAPID privadas en la interfaz o en GitHub.
3. Revisa la URL del proyecto incluida en `schedule-push-reminders.sql` y ejecuta ese archivo como operador. Crea `pg_cron` y `pg_net`, programa `orquivia-push-reminders` cada hora en el minuto 20 y marca el servicio como programado. El secreto se lee de la tabla privada al ejecutar, sin copiar su valor al texto del trabajo. Para apagarlo: `select cron.unschedule('orquivia-push-reminders');` y desmarca `scheduled` en la configuración privada.
4. Cada titular entra en **Mi espacio**, guarda sus preferencias y pulsa **Activar avisos en este dispositivo**. El permiso se pide solo tras ese gesto. En iPhone usa Safari → Compartir → Añadir a pantalla de inicio y abre ese acceso instalado (iOS compatible, 16.4 o posterior).

El servidor comprueba cada hora los pendientes por usuaria y envía como máximo un resumen por dispositivo y fecha, a partir de la hora elegida. La ejecución del minuto 20, el proveedor y el dispositivo determinan la llegada; no se promete una hora exacta. `orquivia_push_deliveries` conserva el contenido original, la reserva de ejecución y el resultado para evitar duplicados y reintentar fallos. Los endpoints caducados dejan de estar activos. Los envíos cifrados muestran únicamente «Tienes tareas pendientes»; no incluyen clientes ni importes. El service worker solo gestiona avisos y su apertura: no tiene caché ni intercepta solicitudes de datos. Un proyecto pausado, sin conexión o con permisos del dispositivo revocados no puede entregar los avisos normalmente.

### Correos de empresa independientes

Los avisos dentro del portal se calculan al abrirlo. Los correos requieren su propio servicio y consentimiento, independientemente de los recordatorios personales:

1. Configura Resend con dominio verificado y los secretos Edge `RESEND_API_KEY`, `ORQUIVIA_FROM_EMAIL`, `ORQUIVIA_CRON_SECRET`. Supabase proporciona `SUPABASE_SECRET_KEYS.default` o la antigua `SUPABASE_SERVICE_ROLE_KEY` al servidor; nunca al frontend.
2. Desde la raíz, despliega `supabase functions deploy daily-reminders --no-verify-jwt --use-api`. Se incluye `src/domain.js` para usar exactamente las reglas del portal. La función valida su secreto de cron en cada llamada.
3. Activa pg_cron, pg_net y Vault; en Vault guarda `orquivia_project_url` y `orquivia_cron_secret`. Ejecuta `schedule-reminders.sql`.
4. Nicole activa la casilla y configura el correo para avisos. Sin consentimiento booleano explícito no hay envíos.

Se comprueba cada hora y se envía como máximo un resumen **por empresa**, entre 09:00 y 19:00 de Europe/Madrid, aunque haya dos cuentas. `orquivia_team_reminder_deliveries` conserva el mensaje para reintentos idempotentes. Si cambia el destinatario, se cancela el reintento al anterior. No se escribe a clientes. No hay conexión bancaria ni garantía de entrega; consulta logs de Edge, Cron y entrega, y considera que un proyecto pausado no puede enviar. Para apagar el trabajo: `select cron.unschedule('orquivia-daily-reminders');`.

## Verificación local

`202610140010_tax_records_missing_receipts.sql` añade la colección opcional `taxRecords` y `missingReceiptReason` en gastos. Valida declaraciones de resultado cero, pagos y devoluciones confirmados, referencias a suplidos existentes y los límites de los documentos. Los originales fiscales usan el mismo bucket privado, con verificación de organización, archivo, tamaño y MIME en cada guardado. La protección frente al borrado de originales vinculados examina gastos y declaraciones, bajo el mismo bloqueo de fila de los guardados. La auditoría reconoce la entidad `tax` y el motivo de falta de ticket; conserva los permisos anteriores, MFA e identidad esperada. La migración no añade ni modifica registros históricos por sí sola.

`202610150011_prepared_quotes.sql` añade `ready` (**Preparado**) solo para presupuestos numerados. La RPC de emisión asigna `ready` al presupuesto y conserva `issued` en las facturas. El nuevo validador delega en la cadena completa anterior, mapeando exclusivamente ese estado de presupuesto durante la validación; conserva el tamaño máximo real del estado. Los números y fechas emitidos, los datos fiscales de facturas, el CAS, la membresía, MFA y la auditoría siguen protegidos. Los presupuestos ya enviados conservan su estado y se pueden marcar como preparados explícitamente; no se envían correos al cliente ni se reescriben históricos al aplicar la migración. Tras cambiar las reglas de avisos en `src/domain.js`, vuelve a desplegar los servicios Edge de correo y push para que incluyan esa versión compartida.

`npm test` prueba dominio y cliente con transporte simulado. Para ejecutar PostgreSQL real en memoria sin Docker:

```powershell
npm install --prefix supabase/.verification --no-save --no-package-lock @electric-sql/pglite
node supabase/tests/team-postgres.mjs
node supabase/tests/personal-postgres.mjs
node supabase/tests/push-runtime-postgres.mjs
node supabase/tests/record-history-postgres.mjs
node supabase/tests/tax-records-postgres.mjs
node supabase/tests/prepared-quotes-postgres.mjs
node supabase/tests/document-mail-postgres.mjs
```

Los conjuntos de PGlite comprueban acceso compartido, RLS, MFA, CAS, fechas/importes, bloqueo fiscal, numeración e importación, auditoría, correo por empresa, revocación, gastos y originales privados. También comprueban perfiles y fotos solo de su titular, límites y propietarios de dispositivos, objetivos de envío autorizados, reservas diarias, configuración VAPID privada, inicialización protegida por transacción y rechazo de peticiones cuya identidad inicial difiere del JWT final. Las comprobaciones de gastos rápidos incluyen proveedor opcional, IVA desconocido, abonos, importes adicionales y movimientos de caja separados. El conjunto de historial comprueba autoría derivada de la sesión, campos modificados, cobros asociados, conservación de auditoría anterior, un tercer miembro autorizado, ausencia de cambios tras un conflicto y rechazo de escritura directa, de usuarios ajenos y de sesiones sin MFA. El esquema de Storage del runner representa las políticas SQL, sin ejecutar el gateway de Supabase Storage. PGlite usa una conexión exclusiva: no prueba carreras reales entre conexiones, Supabase Auth/gateway, JWT reales ni la entrega de cron, correo o push en un iPhone. `tests/workspace_security.sql` añade pgTAP para `supabase test db` en el entorno local completo. Antes de producción, prueba las dos cuentas, una ajena, dos ventanas editando, recuperación de acceso, archivos privados y registro/baja de un dispositivo real; no reinicies una base real para ejecutar tests.
